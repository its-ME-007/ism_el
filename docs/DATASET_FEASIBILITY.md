# Public Dataset Feasibility for Semantic Demand Experiments\n\n**Review date:** 2026-10-31\n**Question:** Can a Hugging Face dataset pair document text with access history well enough to run the product's future-demand experiment?\n\n## Recommendation\n\nDo not replace the enterprise-shaped synthetic trace benchmark with a public Wikipedia dataset as if it were equivalent to enterprise file access. A bounded pairing has now been measured: all **100/100** titles in the latest-day sample (2026-10-28) resolved to one English Wikipedia page and text record, with no title ambiguities or misses. We then fetched the latest historical revision strictly before the target day for each page. **38/100 pages (38%)** had a revision and text available before the cutoff; **62/100** had no pre-cutoff revision. The current-text snapshot is mostly future relative to the target, and the historical text subset is selected by page age. Neither is sufficient for an unbiased causal model evaluation. Keep synthetic traces for policy/simulation development and report any public page-view findings separately as web-attention proxy results.\n\nFor a substantive semantic tiering claim, the best data remains real document text plus file-system access logs and tier/cost information from the target environment. No reviewed Hugging Face candidate supplies those together.\n\n## Candidate comparison\n\n| Candidate | Text | Demand/access signal | Join | Scale and limitation | Fit |\n|---|---|---|---|---|---|\n| [vtasca/wikipedia-pageviews](https://huggingface.co/datasets/vtasca/wikipedia-pageviews) | No article body; article title only | Daily page views, 2016-01-01 through 2026-10-26 in the reviewed card | By article title to a text snapshot; requires title normalization and ambiguity checks | About 394k rows / 15 MB, but only the 100 most popular pages are recorded each day. A missing page is censored/unknown, not zero. | Best bounded time-series pilot, with strong selection bias |\n| [NeuML/wikipedia-20260401](https://huggingface.co/datasets/NeuML/wikipedia-20260401) | English article text, ID, URL, title | `pageviews.sqlite` is described as aggregated per-page views | Potentially direct by page ID, but SQLite schema and aggregation interval still need inspection | About 26.4 GB total; the SQLite file alone is about 2.06 GB. Aggregated views do not establish a future 24-hour target. | Better for a content/popularity association, not temporal demand prediction |\n| [HuggingFaceFW/finewiki](https://huggingface.co/datasets/HuggingFaceFW/finewiki) + [raw Wikimedia time series](https://huggingface.co/datasets/jeremycochoy/wikimedia-pageview-timeseries-raw) | FineWiki has English text, `page_id`, title and `date_modified` | Raw time-series files have dated hourly/daily columns | Not proven: FineWiki uses numeric page IDs; raw card documents a numeric `index` (not explicitly the same ID) and a sanitized title+SHA256 `key` | Raw repository is documented as about 640 GB; available hourly/daily windows are largely 2011-2016, while current FineWiki text can be newer. | Poor first choice until identifier semantics and time-safe content are verified |\n\n## Bounded pilot constraints\n\nThe `vtasca` dataset is small enough to inspect and process without downloading a huge corpus. Its daily records are already page-ID-free titles and view counts. A text adapter could normalize underscores and URL/title encoding, then join against a Wikipedia snapshot. Before modeling, it must measure exact, normalized, ambiguous, and unmatched title counts.\n\nHowever, do not fill missing article-days with zero: absence from a top-100 list only establishes that the article was not included in the dataset. A valid pilot should either model only observed ranked rows with an explicitly conditional target, or find a complete page-view source for the selected article IDs. Any result is about Wikipedia readership, not enterprise file accesses.\n\nThe repository includes a local join-coverage utility and a historical text fetcher. It has been run on the 100 rows from the latest day in the downloaded CSV, first against current API text and then against the latest pre-cutoff revision for each page. Reports are at `results/metrics/wikipedia_top100_join_report.json` and `results/metrics/wikipedia_top100_asof_join_report.json`. To repeat the title and historical coverage validation:\n\n```powershell\npython -m src.tiering.ingestion.validate_wikipedia_join `\n  --pageviews data/raw/wikipedia/pageviews.csv `\n  --documents data/processed/wikipedia_top100_asof.jsonl `\n  --output results/metrics/wikipedia_top100_asof_join_report.json\n```\n\nTo refetch the historical text (small sample only; the script throttles requests and resumes successful rows):\n\n```powershell\npython -m src.tiering.ingestion.fetch_wikipedia_asof `\n  --documents data/processed/wikipedia_top100_text.jsonl `\n  --cutoff 2026-10-28 `\n  --output data/processed/wikipedia_top100_asof.jsonl\n```\n\nIt streams the document titles, reports unique and per-observation match/ambiguity rates, and includes a conservative revision-date check: for page-view target date D, it counts text as time-safe only when the recorded revision timestamp is before D. The historical fetcher asks Wikimedia for the latest revision before midnight UTC at the start of D. It does not create labels or impute absent article-days. The full 15 MB page-view CSV is saved at `data/raw/wikipedia/pageviews.csv`; the latest-day slice and retrieved text samples are saved beside it and under `data/processed/`.\n\nThis measured sample is a direct pairing of the page-view CSV and English Wikipedia API records, not a FineWiki join. The title join is **100/100 (100%)**; the historical, pre-cutoff text coverage is **38/100 (38%)**. Sixty-two titles had no revision before the cutoff, so their semantics cannot be observed at prediction time. This historical subset has survivorship bias and is **not ready for an unbiased model evaluation**. A larger sample drawn from pages known to exist before the cutoff, paired with a complete demand signal, is needed before a temporal semantic benchmark.\n\nThe `NeuML` snapshot is dated 2026-04-01. If it is used as text for page-view prediction, restrict prediction cutoffs to after that snapshot (and preserve article modification/version timing where available). Do not apply its present-day text to the 2016 history and describe the result as time-causal.\n\n## FineWiki/raw time-series join status\n\nThe cards establish that FineWiki has `page_id`, `title`, `text`, and `date_modified`. The raw page-view card documents a numeric `index`, a string `key` formed from a sanitized title and hash, and dated columns. It does not define `index` as Wikimedia `page_id`, nor publish the hash construction in its schema. The raw parquet is too large for this first check, and the Hugging Face viewer is unavailable because the table has 1,028 columns. **No successful join rate has been measured; do not treat this pair as validated.**\n\nEven if the join is proven, the documented 2011-2016 page-view windows predate most FineWiki article text versions. Filter content by `date_modified <= prediction_cutoff`, use a matching historical text snapshot, or exclude the affected examples. Otherwise semantic inputs can contain later edits than the access window.\n\n## Next data step\n\n1. Use the `vtasca` CSV's small size to measure title overlap against a matching Wikipedia text snapshot; report match rates and duplicate/collision handling.\n2. Inspect the NeuML SQLite schema separately before deciding whether its aggregated page-view signal can support a narrowly stated popularity association.\n3. Proceed to a public temporal pilot only if text timing and the target's observation/censoring rules are defensible. Keep all public-page-view conclusions separate from enterprise-tier claims.\n
